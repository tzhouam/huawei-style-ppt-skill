# 可编辑演示文稿与证据页

用于 PPTX、Google Slides，或从现有 deck 增量修改。视觉色板和字号仍以 [华为式风格 preset](ppt-style-huawei.md)及用户给的参考稿为准。

## 建稿与改稿

1. 先读取整套页面、备注、批注和内嵌媒体。明确哪份文件是最新版，列出将保留、合并、替换的页面。不要为了统一风格覆盖用户刚修改的内容。
2. 记录实体表：团队、产品、组件、Agent、仓库、外部平台分别叫什么、谁执行哪一步。页面标题和封面沿用这一表；不要把团队名缩写成产品名。
3. 将每页写成“主张 → 证据 → 限制”。事实变了要同步修改标题、图表、截图说明、讲稿与页脚；仅替换一个数字会留下自相矛盾的页面。
4. 既有 deck 是模板时复制其页面尺寸、边距、标题层级、色板、图例与页脚；新页面只引入有意义的视觉差异。

## 原生对象与 draw.io 风格流程

- 流程节点、箭头、泳道、标签、图例和结论用原生形状与文本。箭头应是单段或明确的正交路径，不用断裂的数段线模拟一条关系。
- 一个节点表达一个动作；箭头表示任务或证据的实际方向。共享知识、规则或数据源只画一个节点，再分别连到使用者。环节与执行者分开：例如“测试”是环节，“Agent 检索日志”是执行动作，“维护者确认根因”是决策。
- 可选语义配色：AI 执行用浅红、人工判断用白底、项目知识用浅蓝、系统记录用中性灰；边框和文字遵循整套 deck 的色板。颜色之外也写角色标签，避免只靠色彩识别。
- 同级节点尺寸、对齐、内边距、标题字号一致；文字放不下先改短或重排。并列陈述用项目符号，流程步骤用动词短语，不用硬凑等长短标题。
- 把“优势”具体写在步骤旁：哪项搜集、定位、复核或追踪工作改变了；不要只写“更智能、更高效”。若只有设计意图、没有运行证据，标为目标或待验证。

## 真实案例与数据

- 产品界面、终端、PR Review、Issue、CI 和看板要用真实截图，保留编号、标题或时间，让听众认得来源。截图可裁剪突出关键区域，但不可改写原始结果。截图旁使用可编辑文字说明“触发 → 动作 → 结果 → 边界”。
- 运行案例区分：已发布、已合入、仅本地回归、尚未执行端到端测试。作者回复、修复提交、最终合入是不同事件，不要合成一个“采纳”数字。
- 汇总图注明样本定义、起止时间、状态快照、单位和数据来源。比较两组时说明分母、匹配条件、尚未完成项和非因果性；不能以日志任务数替代唯一 PR/Issue 数。
- 图表尽量保持数据和标签可编辑。若引用既有统计图为图片，标明冻结日期和来源，先核对图例与标题是否对应同一指标。

## 排版与媒体

- 输出要兼顾投影与会后阅读。主内容在实际显示尺寸下可读；来源可小一些，但不能为塞满一页把主体文字压到脚注字号。检查中英文换行和字体回退，尤其是 Microsoft YaHei。
- 普通文本黑或深灰，红色用于页面标题与真正需要强调的结论；整宽红色底条不是必备组件。可点击来源文本仍应保持所在层级的正常颜色。若编辑器强制蓝色下划线，可把链接放在图片或透明点击区上。
- 视频使用可播放的原片或可接受的转码版本，检查源帧本身的清晰度，而不只看输出分辨率。PPTX 交付时确认媒体真实内嵌；Google Slides 则确认访问权限、播放方式和导入后的表现。
- 页码按最终页序重新生成。合并或删除页面后，检查页内引用和备注中的旧页码。

## 验收

1. 用原生工具打开成品，再导出 PDF/逐页图片做视觉复核；至少看封面、复杂流程、最密表格、每种截图页、视频页和结尾，并并排浏览全稿。
2. 检查文本/形状是否可单独选中，链接是否能打开，媒体是否播放，图表是否显示正确。使用 `scripts/check_pptx.py deck.pptx` 发现明显越界、页码不连续、整页图片和嵌入媒体问题；其警告需要人工判断。
3. 比对原始记录与最终表述，尤其是名称、PR/Issue 编号、日期、分母和“已上线/待验证”。把尚未证实的结论留作限制，不靠漂亮版式掩盖它。
